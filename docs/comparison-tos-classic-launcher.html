Two launchers for the same game

Yufa ToS Classic launcher (this repo, yonlu/tos-yufa-launcher, 1.0.0) against lukkas71/tos-classic-launcher (0.1.16). Both are Electron launchers for a Tree of Savior private server. Read on 2026-09-06, from the code, not the READMEs.

The short version. These two projects solved different problems and each is honest about which one. Yufa built a distribution pipeline: content-addressed blobs on Cloudflare R2, immutable per-build manifests, rollback, garbage collection, and an end-to-end rehearsal that drives the packaged installer. The lukkas71 launcher built a trust model: Ed25519-signed manifests, an anti-rollback watermark, a signed self-update document with a second SHA-512 check, and a C# helper that verifies Microsoft's Authenticode on every redistributable before it runs under UAC.

Yufa can ship a 13 GB game today and roll it back tomorrow, but a compromised CDN could feed its players anything. The lukkas71 launcher would reject that tampered manifest, but it has no way to get files onto a CDN in the first place, downloads one file at a time, and re-hashes the whole 16 GB install every time it runs. If I had to pick one to put in front of players this month it would be Yufa. If I had to pick one to borrow ideas from, it would be the other one, and specifically its signing layer.

What each one actually is

Yufa is a launcher plus the whole publishing side. The operator runs yufa-publish release --dir against a clean game folder; the CLI hashes every file (with a mtime-keyed cache so the second run is fast), skips blobs the bucket already has, uploads the rest with 64 MiB multipart parts, writes manifests/<build>.json, and only then flips manifest.json. A player who is mid-download when a new build lands never sees a file change underneath them, because the file they are fetching is addressed by its own hash. That ordering is the whole design and it is written down in docs/adr/0001-content-addressed-blobs.md.

The repo also carries evidence of having been run for real. GOLIVE.md records the rehearsal on 2026-09-06: the discovery that uploads from the operator's laptop to Cloudflare corrupt with bad record mac unless WARP is on, that objects over 512 MB bypass the free-plan edge cache (8 files, 9.6 of 12.7 GB in Build 1), and that UseSteamClient="NO" in client.xml lets 10 MB of Steam DLLs be excluded. Those are not things you learn from a design doc.

lukkas71 is a launcher plus a security model, and it stops at the edge of the CDN. The manifest has a sequence, an expiresAt, a signature block, and a 27-line canonicalization module shared between the signer, the validator, the updater and the self-updater (shared/manifest-signature.mjs). Nothing in the engine trusts a URL, a hash or an obsolete entry until the signature has passed. That is the right order and Yufa does not do it.

But the README's own bold warning says the only signing key is local-dev-2026, the production config ships with trustedKeys: {} so it cannot accept any manifest at all (config/launcher.config.json:16-17), both production endpoints are documented as not yet implemented (docs/DEPLOYMENT.md:55-60), and there is not a single line of code that uploads anything anywhere. I grepped for R2, S3, wrangler, aws, rclone. Zero hits. Seventeen releases in nine days and every one of them was local.

Distribution model

Yufa: content-addressed

  • Key is objects/<sha256>. Identical files across builds stored once. Re-releasing after a one-file change uploads one blob (commands.ts:130-133 skips blobs that already exist).
  • Every build's manifest is kept immutably under manifests/. Rollback rewrites manifest.json with the stored text, nothing else (commands.ts:240-251).
  • gc --keep N deletes blobs that none of the N newest builds nor the current one reference. It refuses to run if any other prefix sits under objects/ (commands.ts:351-365). Manifests and redist/ are never touched.
  • Build numbers come from max(current, stored...) + 1, so a rollback can never cause a number to be reused (commands.ts:97-99).
  • Redistributables deliberately break the rule: path-keyed, overwritten, no-cache, index written last (ADR 0002). The tradeoff is argued, not hidden.

lukkas71: path-mirrored

  • URL equals the game-relative path (scripts/manifest-lib.mjs:133-138). Two releases sharing data/001.ipf either duplicate the whole tree per releaseId or mutate in place. The docs say "do not mutate". The code cannot stop you.
  • obsolete[] is computed by diffing against --previous-manifest. Forget the flag and old files stay on disk forever.
  • No garbage collection of published payloads. clean-generated.mjs only prunes the local .work folder.
  • No rollback command. Policy is roll-forward with a higher sequence; nobody wrote the tool that builds such a manifest.
  • Mirrors are first-class: mirrors[] in the manifest, tried in order after three failed attempts on the base URL (engine.ts:340-376). Yufa has exactly one blob host and no fallback.

I think Yufa got this right and the ADR explains why in six sentences. Content addressing costs you a browsable bucket and forces you to write gc. In exchange you get atomic publishes and free rollback. The lukkas71 approach is what you do when the CDN is somebody else's problem, which in that project it is.

Trust model

This is where the projects swap places.

Yufa's position is defensible for a private server with one operator and a bucket only that operator can write to. It is also one leaked R2 token away from being indefensible. Adding an Ed25519 signature over the manifest would cost a day and change nothing about the content-addressed design. The lukkas71 canonicalizer is small enough to read in one sitting and would port cleanly.

The lukkas71 side has the reverse problem. The security model is thorough on paper and half-wired in practice: the trusted-key map is empty, allowUnsignedInstaller: true replaces electron-updater's signature check with a function that returns null (launcher-self-update.ts:151-154), and that flag is set in the online-live-test profile too, not just the localhost lab.

The separate-process design in lukkas71 is the one architectural idea I keep coming back to. ADR-002 says the goal is a replaceable boundary, so the agent could be rewritten in Rust without touching the UI. It also means a renderer compromise cannot reach the filesystem directly. Yufa's headless engine with injected fetch is a cheaper way to get the testability half of that benefit, and its test count shows it worked.

Publishing and operations

Yufa

  • Eight CLI commands. Three store backends behind one interface: R2, a local directory (used by every test), and dry-run.
  • A hard guard the operator cannot configure away drops user.xml, chat configs, CheatLogData, logs, screenshots and 15 runtime folders from every release (tree.ts:34-45). The E2E sandbox plants bait copies of these and asserts they never reach the bucket.
  • verify --mirror re-hashes the local game folder for real, bypassing the cache, and requires agreement in both directions.
  • A dev server that lies on purpose: flips a byte mid-stream, kills the socket after N bytes, ignores Range (tools/dev-server.ts:99-115).
  • npm run e2e drives the packaged .exe through install, update and rollback, screenshots each step, and checks the Install Record and file hashes afterwards.

lukkas71

  • Generate, sign, validate, serve. The validator is worth stealing: it re-implements the contract independently of the runtime zod schema and is stricter, probes remote hosts concurrently, and has a --check-range mode that demands a 206 and cross-checks Content-Range.
  • A 38-glob exclude list plays the role of Yufa's hard guard, but it is a default the operator can override with --include.
  • No upload. No rollback tool. No GC. The runbook's step "escolher storage e enviar os arquivos" is still pending (RELEASE_READINESS.md:58).
  • A PowerShell diagnostics collector and JSON-lines logs rotated at 5 MB. Yufa uses electron-log and an "open logs" link.
  • Twenty-two docs, 3,336 lines. A per-file source map. A handbook. This is more documentation than code, and much of it describes things that are planned rather than built (the bootstrapper doc is 148 lines for a component whose first line says it does not exist).

Windows runtimes

Both projects noticed that the 32-bit client needs VC++ x86 and the June 2010 DirectX, and both refuse to run the launcher itself elevated. They diverge on everything else.

Yufa probes for vcruntime140.dll and d3dx9_43.dll in SysWOW64, and only if one is missing does it download a trimmed six-file installer set from the bucket, verified by size and sha256 through the same engine as game files. A generated PowerShell script runs the installers under one -Verb RunAs and writes exit codes to a result file because an elevated process cannot pipe back (redist.ts:181-249). Declined UAC is a warning; Play stays enabled. The set ships outside the game, so players who already have the runtimes never download a byte of them.

lukkas71 ships the entire _CommonRedist folder as part of the game manifest (13 packages, VC++ 2005 through v14), so every player downloads it whether they need it or not. Detection is better: registry queries for the older VC++ years and a numeric compare against 14.50.35719.0 for v14, rather than DLL presence. The installer is a 404-line C# helper that re-launches itself with runas, confines every path to _CommonRedist, and refuses to run any installer whose Authenticode subject is not Microsoft and whose WinVerifyTrust fails (TosClassicPrerequisiteInstaller.cs:234-246). Receipts keyed by installer hash prevent re-runs. That is a real security control Yufa lacks: Yufa trusts an unsigned index.json to tell it which executable to elevate.

The cost is that the helper needs .NET Framework 4's csc.exe at build time, and pnpm build chains it first. The lukkas71 launcher cannot be built on macOS or Linux at all (build-prerequisite-helper.mjs:26-31). Yufa builds anywhere and only its E2E smoke needs Windows.

Testing and process

Yufa has 154 test cases across 9 files, and the distribution is right: 33 on the patcher state machine, 39 on the CLI against a local store, 15 on the download engine using the fault-injecting dev server, 18 on the pure plan function. Then the packaged-exe smoke on top. Nothing on the renderer. The spec (docs/specs/2026-09-05-full-install-and-updates.md) names five seams to test in priority order, which is the kind of thing that only gets written when someone intends to follow it.

lukkas71 has 48 cases in 16 files. The path-safety module, which the whole delete story depends on, gets one 16-line test. Desktop tests are excluded from typecheck (apps/desktop/tsconfig.json:8). The changelog and readiness doc both say 52; I counted 48. Small thing, but it tells you the number was typed, not measured.

Neither repo has CI. Neither has a linter. Yufa has 27 commits through 10 PRs with review-fix commits visible in the log. The lukkas71 repo has three squashed commits from one author, no PRs, and a CONTRIBUTING.md that names eight sensitive areas requiring extra review with no mechanism to trigger one. The docs are extensive and in places contradict the code, which is the failure mode of writing docs ahead of the implementation.

What I would take from each

Into Yufa, from lukkas71

  • The Ed25519 manifest signature and canonicalizer. Highest value, lowest cost. Keep rollback working by signing every stored manifest and dropping the sequence check; the signature alone stops a tampered bucket.
  • Authenticode verification of redistributable installers before elevating them. Yufa currently elevates whatever an unsigned index names.
  • CSP as a header with connect-src, an https-only host allowlist for openExternal, a will-navigate handler, and env overrides gated on !app.isPackaged.
  • Mirrors. Even one fallback host would remove Yufa's single point of failure.
  • The Discord presence card, if the server has one.

Into lukkas71, from Yufa

  • Content addressing and manifest-last publishing. It makes rollback trivial and the "files must be immutable" rule enforceable.
  • A pure plan function with an Install Record. It replaces the 16 GB re-hash with a size + mtime + recorded-hash check and makes the engine testable without a filesystem.
  • Parallel downloads and a disk-space check. Both are table stakes for a 13 GB install.
  • Any upload path at all. The S3 SDK against R2 is about 90 lines in store.ts.
  • An E2E that drives the packaged installer. The current tests never touch the built artifact.

Things both get wrong

  • No CI. Two projects with a combined 200 tests and nothing runs them on push.
  • No HTTPS enforcement on the game manifest URL. Yufa accepts http:// from the schema; lukkas71 accepts it from the engine and only guards the self-update feed.
  • style-src 'unsafe-inline' in both CSPs, for the same reason (inline progress-bar widths).
  • No renderer tests in either.
  • No signed installer in either. Yufa documents the SmartScreen prompt as expected. lukkas71 requires a certificate in config and so cannot produce a production build until it buys one.
  • Portuguese-only docs in both, which is fine for the audience, and worth saying out loud if either wants outside contributors.

Bottom line

Yufa is a shipping pipeline with a trust gap. The lukkas71 launcher is a trust model with a shipping gap. Yufa's gap is a day's work with a well-understood primitive. The other project's gap is an upload tool, a concurrency rewrite, a plan step, a certificate purchase, two backend endpoints, and a production key, and none of those has been started. If the two authors ever compared notes, the merged design would be obvious: Yufa's bucket and CLI, signed with lukkas71's manifest layer, in front of a UI that borrows the Discord card and leaves the DXVK feature for version two.
